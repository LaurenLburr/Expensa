# Key Architectural Decisions

## Transaction Identity Management

`TransactionId` is now **repository-managed**.

Rules:

* IDs are generated by the **database**
* the **repository assigns the ID back to the domain object**
* UI and domain objects **must not create IDs**

This prevents accidental mutation of primary keys.

Example flow:

1. UI creates Transaction object without ID
2. Repository inserts row into database
3. Repository reads `last_insert_rowid()`
4. Repository assigns the ID back to the object

# Transaction Storage

## Table: `Txn`

Purpose:

Stores all financial transactions created by budgeting, imports, or manual entry.

Primary columns:

| Column        | Description                        |
| ------------- | ---------------------------------- |
| TransactionId | Primary key                        |
| AccountId     | Account the transaction belongs to |
| PayeeId       | Associated payee                   |
| Status        | Transaction lifecycle state        |
| Amount        | Transaction amount                 |
| StartDate     | Date associated with transaction   |
| Confirm       | Optional confirmation text         |
| Note          | Optional note                      |

---

# Transaction Status Lifecycle

Transactions move through controlled states.

Current lifecycle:

```
Projected → Outstanding → Cleared
```

Rules:

* **Projected**
  Budget entry exists but transaction not created.

* **Outstanding**
  Transaction created but not cleared.

* **Cleared**
  Transaction finalized.

Once **Cleared**, automatic transitions stop.

Corrections must be handled manually.

---

# Transaction Status Audit Log

## Table: `TxnStatusLog`

Purpose:

Tracks all status changes applied to a transaction.

This creates a **complete audit trail** for debugging and financial history.

Columns:

| Column         | Description                         |
| -------------- | ----------------------------------- |
| TxnStatusLogId | Primary key                         |
| TransactionId  | Associated transaction              |
| OldStatus      | Previous status                     |
| NewStatus      | New status                          |
| ReasonCode     | Enum name describing reason         |
| ReasonText     | Optional explanation                |
| ChangedUtc     | Timestamp of change                 |
| ChangedBy      | Future user tracking                |
| Source         | Origin of change (UI, import, etc.) |

---

# Enum Storage Rule

Enums are stored **by name** rather than numeric value.

Example:

```
ManualCorrection
StatusReset
MarkedInvalid
```

Reasons:

* protects long-lived data from enum reordering
* makes database records human readable
* simplifies debugging

Enum definitions remain **only in code**, not in database tables.

# Planned Repository Method

Future method in `ITransactionRepository`:

```
ChangeStatus(
    int transactionId,
    TransactionStatus newStatus,
    TransactionChangeReason reasonCode,
    string? reasonText,
    string source)
```

Responsibilities:

1. Read current transaction
2. Update transaction status
3. Insert entry in `TxnStatusLog`

This ensures **every status change is recorded**.

# SQL Query Strategy

All SQL statements are stored in the **SqlQuery catalog table**.

Rules:

* SQL stored centrally
* application references queries by name
* updates use `INSERT OR REPLACE`
* identifiers may use `[ ]`
* SQL keywords **must not be bracketed**
